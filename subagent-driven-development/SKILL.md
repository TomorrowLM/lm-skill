# 子智能体驱动开发

把实现计划拆成多个独立任务，并为每个任务分派一个全新的子智能体。每个任务都必须先做规格审查，再做代码质量审查，并在结束前有真实验证证据。

## 适用场景

适合：
- 任务清单已明确拆分为 2 个以上相对独立的子任务。
- 每个任务都将由一个全新的子智能体独立实现和验证。
- 需要避免主会话历史污染和“顺手做其他任务”。
- 需要统一的审查节奏：规格先过、质量后验收。

不适合：
- 任务高度耦合，无法清晰拆分。
- 实际仍由主会话直接读写并验证代码。
- 只是“做得多一点”“分几个步骤”而没有真实子任务边界。
- 计划尚未形成或不够明确。

## HARD-GATE

以下规则无例外，即使用户说“先做”“很简单”“先手动试试”“直接在主会话里做”：

1. 如果没有明确的任务拆分，且每个子任务不对应独立的子智能体，不使用 `subagent-driven-development`。
2. 如果只是把一个单文件修改拆成几个步骤，但仍然由主会话直接实现、直接验证，不使用该技能。
3. 如果没有规格审查和代码质量审查的两阶段流程，不使用该技能。
4. 如果只是在说“并行”“多代理”，但没有真实子任务边界和独立执行，不使用该技能。

只有在“拆分成可独立交付的子任务 + 新子智能体 + 两阶段审查 + 真实验证”都成立时，才可进入该技能。

## 核心原则

- 一个任务对应一个全新子智能体。
- 子智能体不能继承主会话隐式历史，只能接收当前任务的完整上下文。
- 每个任务都必须经过两阶段审查：规格合规性审查，然后代码质量审查。
- 任务完成前必须有验证证据，不能只凭“看起来没问题”。

## 红线

绝不：
- 在没有真实分派隔离子代理的情况下，宣称自己在使用 `subagent-driven-development`。
- 把主会话直接实现的结果描述成“子代理完成的任务”。
- 在已明确选择隔离工作区时，跳过必要的隔离准备直接开始实现。
- 没有真实验证证据就标记任务完成或宣称整体完成。
- 让子智能体读取计划文件而不是完整任务上下文。
- 只在口头说“并行/多代理”，但没有真实子任务边界和独立执行。
- 跳过审查或在任一审查未解决前进入下一个任务。
- 在规格审查通过前开始代码质量审查。

如果子智能体提问：
- 需要清晰完整地回答；必要时补充额外上下文。

如果审查者发现问题：
- 实现者必须修复，并重新审查，直到通过。

## 执行流程

1. 确认存在可执行计划；没有则先形成计划，禁止分派子智能体。
2. 默认保留在当前工作区；只有用户明确要求隔离，或任务确实需要隔离时，才切换至隔离工作区。
3. 要求实现子智能体先写可失败的测试，再实现功能并完成验证。
4. 实现子智能体完成实现、测试、自审后，立即交给规格审查子智能体。
5. 规格审查通过后，再交给代码质量审查子智能体。
6. 代码质量审查通过后，执行最终验证并记录可复查的结果。
7. 只有在两阶段审查和验证都通过后，才标记任务完成。
8. 所有任务完成后，执行整体验证，并按项目流程收尾。

## 子智能体的硬约束

1. 不继承当前会话历史。
2. 只处理当前分派的那一项任务。
3. 每个任务使用一个新的子智能体。
4. 由主控制者决定上下文、重派和审查时机。

## 结论

本技能的核心不是“让 AI 多跑几个子代理”，而是：
- 任务边界清晰，
- 上下文隔离，
- 审查顺序固定，
- 验证必须真实。

因此，它是“显式任务拆分 + 独立子智能体 + 两阶段审查 + 真实验证”的组合条件，不是单纯为了节省 token 或为了看起来更复杂。

只有在这些条件都成立时，才应使用 `subagent-driven-development`。
