# 反例示范与速查表

SKILL.md 之外的三份速查参考：写错的样子、自由度判断、常见层错位。正文中的原则和规范见 SKILL.md。

## 反例：写给人看的 Skill

假设你要做一个"代码审查"技能：

```markdown
---
name: code-review
description: 代码审查技能
---

## 背景
本技能基于团队多年的代码审查经验总结而成，旨在提升代码质量和团队协作效率。

## 审查原则
- 保持专业、建设性的语气
- 关注代码质量而非个人风格
- 平衡严格性和灵活性
```

从 AI 视角审视为什么这是错的：

| 写法 | 为什么对 AI 无效 |
|------|-----------------|
| "基于团队多年经验总结" | AI 不关心来历，只需知道怎么做 |
| "保持专业、建设性的语气" | "专业"和"建设性"对 AI 是无限模糊空间 |
| "平衡严格性和灵活性" | AI 没有这种直觉，等于没说 |
| "全面审查，给出改进建议" | AI 需要的是：先查什么、再查什么、什么必报、什么可忽略 |
| "版本记录 v1.0/v1.1" | AI 每次全新唤醒，版本号无意义 |
| description 只写"代码审查技能" | "帮我看看这段代码"要不要触发？太模糊 |

**根因**：每一条单独看都不是"错"，但它们是写给人看的。对 AI 来说，正面描述"做什么" → 无限可行域；反例清单"不做什么" → 收窄行为边界。

反面写法：把模糊要求转为可检测的 checklist——

```markdown
## 审查步骤
1. 检查是否有未处理的 error 分支
2. 检查是否有硬编码的密钥或 token
3. 检查是否存在 N+1 查询
4. 检查函数是否超过 40 行 → 建议拆分
5. 忽略：命名风格偏好、空行数量、注释格式（除非导致歧义）
```

## 自由度判断速查

| 判断维度 | 低自由度 → 脚本 | 高自由度 → 文字指令 |
|----------|----------------|-------------------|
| 每次结果必须一样 | ✅ | — |
| 涉及精确格式/长度约束 | ✅ | — |
| 涉及命名规范转换 | ✅ | — |
| 需要校验规则匹配 | ✅ | — |
| 同样代码每次重写 | ✅ | — |
| 需要理解上下文 | — | ✅ |
| 多种合理做法 | — | ✅ |
| 需要创造性判断 | — | ✅ |

两个错误方向：
- **脆弱任务给太多自由**：比如生成 YAML，short_description 写成 65 字符 — 产品截断。用脚本锁死。
- **创造性任务给太多约束**：比如"第一段必须以'昨天'开头" — 生成文本像填词。给结构比例，不锁具体用词。

## 常见层错位

| 错误 | 后果 | 修正 |
|------|------|------|
| 触发条件放在 body 里 | body 触发后才加载，晚了 | 放 frontmatter description |
| "When to Use" 写在 body | 同上 | 移到 description |
| 参考细节塞进 SKILL.md | body 膨胀，信息密度下降 | 拆到 references/ |
| 确定性操作写成文字指令 | AI 每次重新理解，可能出错 | 封装成 scripts/ |
| references 互相引用 | AI 需多跳获取信息 | 从 SKILL.md 直接链接 |
| SKILL.md 与 references 内容重复 | 浪费 token，更新不一致 | 信息只在一处存在 |
