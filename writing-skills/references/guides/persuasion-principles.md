# 抵抗合理化原则

当设计纪律执行类技能，且 AI 可能因为时间、成本、权威或“务实”理由绕过规则时读取。

## 目标

让技能在压力下仍能改变行为，而不是只在学术问答中被正确复述。

## 可用原则

| 原则 | 用法 | 适用 |
|------|------|------|
| 权威 | 使用“必须、禁止、无例外”等明确语言。 | 安全、验证、TDD、发布前检查。 |
| 承诺 | 要求先声明选择、记录待办、逐项完成。 | 多步骤流程、容易跳步的任务。 |
| 稀缺 | 写清“继续之前”“完成后立即”等时序。 | 防止“之后再做”。 |
| 社会认同 | 写清失败模式，例如“没有验证 = 未完成”。 | 建立稳定规范。 |

少用或不用：

- 归属：只在协作语境下使用。
- 互惠：容易像操纵，默认不用。
- 好感：会鼓励迎合，不用于纪律合规。

## 写法

- 不只写“应该做什么”，还要写“不要怎样变通”。
- 直接封堵已观察到的借口：简单改动、时间不够、之后再补、已经手测、遵守精神即可。
- 把关键规则写成触发条件 + 必需行动：当 X 时，必须 Y。
- 明确失败定义：违反字面，就是违反精神。

## 压力场景设计

组合 3 种以上压力，验证技能能否抵抗绕过：

| 压力 | 例子 |
|------|------|
| 时间 | 截止时间、部署窗口、事故修复。 |
| 沉没成本 | 已经写了很多代码，重做代价高。 |
| 权威 | 经理或资深同事要求跳过步骤。 |
| 疲惫 | 一天结束，想快速收尾。 |
| 社交 | 担心显得教条或不灵活。 |
| 务实 | “这次特殊”“先上线再说”。 |

## 结构化逃生路径

只在目标技能预先定义了可逆协作分支时使用。逃生路径可以放宽过程，不能改变安全、验证或不可逆结果的成功标准。

```markdown
## 团队压力下的做法

核心原则：妥协前先完成自己能控制的验证与风险记录。

### 必须先完成
1. 请求短时间盒，把争论变成小实验。
2. 用具体失败和影响说明风险。
3. 记录临时决定、未满足条件和后续负责人。

### 只有技能预先允许时才能继续
- 采用可逆的临时缓解，不宣称完整成功。
- 保留恢复条件和后续验证入口。
- 明确该分支由技能预先定义为合规；AI 不得现场自行宣布“不算违反门禁”。
```

以下情况不得使用逃生路径：

- 会产生未验证、不安全或不可逆的最终状态。
- 只是因为团队、经理、时间或沉没成本要求跳过 HARD-GATE。
- 需要修改成功标准，才能把当前结果称为完成。
- `writing-skills` 尚未观察基线失败，或修改后尚未通过真实智能体压力测试。

## 伦理边界

- 只用于帮助用户实现已认可的质量、安全和流程目标。
- 不制造虚假紧迫感。
- 不用情绪、内疚或讨好来推动合规。
- 如果用户完全理解这个技巧，它仍应服务于用户的真实利益。
