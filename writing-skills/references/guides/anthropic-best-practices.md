# 技能结构原则

当需要设计技能结构、命名、`description` 或渐进式披露时读取。

## 核心原则

- 技能是给 AI 执行的工作流，不是给人阅读的说明书。
- 只写 AI 不知道、且会改变行为的内容。
- `description` 决定是否触发，`SKILL.md` 决定怎么执行，`references` 只在需要时展开。
- 先保证命中和执行，再考虑完整性。

## Frontmatter

- 只保留必要字段：`name` 和 `description`。
- `name` 使用小写字母、数字和连字符。
- `description` 用中文说明“当什么任务/症状出现时使用”。
- `description` 同时写入不适用边界，减少误触发。
- 不在 `description` 中解释完整流程。

## SKILL.md body

- 入口文件只保留触发后的控制逻辑：原则、步骤、红线、何时读取参考。
- 先写决策顺序，再写操作细节。
- 使用祈使语气，避免模糊词：尽量、可以、建议。
- 示例只保留最强的一个；多个弱示例会浪费上下文。
- 超过 250 行时拆分，优先把长示例、背景、模板移到 `references`。

## References

- `references` 承载按需读取的长内容：案例、评分表、方法论、命令说明。
- 从 `SKILL.md` 直接链接目标 reference，不做 A → B → C 深链。
- reference 超过 100 行时顶部写目录。
- 不要让同一规则同时出现在 `SKILL.md` 和 reference。

## Scripts

- 确定性、重复性强、容易写错的操作才放脚本。
- 脚本要有最小可运行入口和失败提示。
- 不为了“看起来完整”放未使用脚本。

## 多智能体与子任务规格设计

在设计多 Agent 协作、MCP 编排或多窗口子任务工作流时，遵循 Token 经济性与上下文隔离原则：

- **隔离执行自给自足**：调度方仅传递资源定位与任务规格，自身不预读下游实现技能；执行方在新会话/子窗口中启动，根据任务规格按需自包含加载所需技能。
- **任务规格独立完备**：子任务规格必须包含独立执行所需的完整上下文与边界，不假设执行方具备主流程的历史记忆。
- **增量/修复任务差异自包含**：后续迭代、返工或局部修复任务应设计为自包含的微上下文（明确差距/缺陷、目标资源范围、具体修改项与所需能力），避免强制执行方重新通读全量历史长规格，防止注意力稀释并节省 Token。
- **避免隐式回溯占位符**：提示词与模板中禁止使用“继承前序清单/参考上文”等让模型跨上下文回溯推断的写作指令；要么直接展开完整字段，要么明确定义仅填变更差量（delta）。

## 常见反模式

| 反模式 | 修正 |
|--------|------|
| 把所有资料塞进 `SKILL.md` | 主文件只留控制逻辑，细节下沉。 |
| `description` 只写技能主题 | 写触发症状和不适用边界。 |
| 用抽象愿景代替步骤 | 写可执行动作和停止条件。 |
| 复制大量通用常识 | 删除，默认 AI 已掌握。 |
| 预置太多选项 | 保留默认路径，少量分支按需展开。 |
| 调度方预读所有子任务技能 | 调度方只传定位与规格，隔离执行方按需自加载。 |
| 增量修复时强制执行方重读全量历史长文档 | 提供自包含的差异上下文，精准列出目标范围与改动项。 |
| 模板中写模糊的“继承/参考上文清单” | 直接展开字段或明确定义 delta 差量规则。 |

## 完成检查

- [ ] 技能解决的是可复用问题，不是一次性任务。
- [ ] 有观察到的失败或明确的测试场景。
- [ ] `description` 能解释何时触发和何时不触发。
- [ ] `SKILL.md` 没有重复 reference 内容。
- [ ] 所有被引用的 reference 和 scripts 都存在。
- [ ] 多 Agent / 子任务编排遵循隔离执行、按需加载与增量上下文自包含原则。
