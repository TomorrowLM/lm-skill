# 测试驱动开发（TDD）

## 何时使用

用于新增功能、修复缺陷、重构及其他行为变更。纯只读审查、解释、文档或格式调整且不改变行为时不使用；配置变更若改变运行行为，则按行为变更处理。

## HARD-GATE

行为变更必须先有失败证据，再修改生产代码；实现后必须运行同一聚焦检查并看到通过。用户说“简单”“紧急”“直接改”或“测试以后补”都不能取消红绿证据。小改动应缩小测试范围，不应跳过测试。

### Agent 执行门控

1. 测试前用一句话声明目标行为、最窄测试命令和停止条件；默认不增加确认轮次。不能说明检查如何区分新旧行为时，不得新增测试或修改生产代码，先做一次就近核对。
2. 单一局部行为默认一个聚焦测试组，相关输入和边界可合并断言或参数化。增加独立切片前必须指出可独立失败的业务契约；文件数、字段数、枚举值数量不构成拆分依据。
3. 扩大测试、搜索或改动范围前，必须指出当前失败、直接受影响的调用方或项目门禁依据；无依据不得扩大。超出用户任务范围或需要新增测试依赖、框架、配置时，先说明成本并取得授权。“更保险”“顺便”“覆盖更多”不是依据。
4. 同一测试入口最多允许两次因启动、导入或配置问题失败的执行；第二次仍未运行业务断言就停止排障，报告两次错误、未验证行为及继续所需授权。切换 runner 或命令不重置计数；不得为完成流程扫描全仓或自行搭建框架。该限额不针对有效业务断言的红绿失败，不得通过跳测绕过。
5. 当前切片绿灯且无后续影响该切片的修改时，必须结束本轮；仅可继续已声明的独立切片或执行有项目门禁、明确影响依据的必要检查。无新增证据不得追加组合测试、相邻模块扫描、全量检查或重复命令；范围内行为未满足时不能借此提前结束。

## 流程

### 1. 选择最小充分测试

先写下一句可验证的目标行为，并选能区分旧行为与新行为的最窄检查：

- 单一局部行为：用一个聚焦测试验证；相关输入、边界值可放在同一测试中，不按断言数量拆循环。
- 多个独立行为：只按独立契约或行为切片拆分，每个切片各自红绿；不为每个字段、枚举值或排列组合机械建测试。
- 共享接口或高影响变更：覆盖新契约和直接受影响的调用方；更广回归留到收尾，且只在项目门禁或影响范围要求时执行。

优先验证可观察行为，不用源码文本断言替代可执行测试。复用仓库现有测试工具和命令，不安装依赖或搭建新测试框架来满足本流程。

如果用户要求的测试频率明显重复（例如每个断言都跑全量套件），先说明聚焦检查与收尾回归的分工，建议每个切片只运行聚焦命令、最终再按需跑更广检查；用户确认仍需额外频次后再执行，不把重复验证当作默认 TDD 步骤。

### 2. 红灯

先写测试，再运行当前切片的最窄命令。预期断言失败才是红灯；启动、导入、编译或测试配置错误不是红灯，应在入口故障预算内先修复测试入口。测试先通过时，确认它能区分新旧行为；不能区分就调整测试。无法建立可重复的失败证据时，停止生产代码修改并报告阻塞。

### 3. 绿灯

只做使当前测试通过的最小实现，然后重跑同一命令。失败就修复当前切片并重跑，不扩展到无关测试。进入下一个独立切片前，先完成当前切片的红绿。

### 4. 必要重构

只做服务当前变更的整理；若重构可能影响行为，重跑同一聚焦检查。不要借重构追加未要求的行为或测试矩阵。

## 结束条件

TDD 在所需切片完成红绿、必要重构检查通过后结束，记录变更范围、测试命令、红灯失败证据、绿灯结果及未解决风险。本技能不调用其他技能，也不把 TDD 结束视为整个任务完成。

记录测试命令和最相关的一行结果即可；避免粘贴无关的完整测试输出。

## 调试

缺陷先用最小回归测试复现，再按上述红绿流程修复。不要把临时手动验证或先实现后补、且从未红过的测试当作红灯证据。
