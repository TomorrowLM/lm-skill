# 单测规则

项目使用 Vitest，只测试稳定纯逻辑和关键契约，不追求覆盖率数字，也不按"每个文件一个测试文件"的方式机械补测试。

## 新增测试前判断

- 这个测试能否防止真实业务回归、旧接口字段回归、路由/菜单/登录态/前置流程契约回归
- 如果生产代码被错误修改，这个测试是否会以清晰原因失败
- 是否已经有上层契约测试覆盖同一行为，能合并就合并，不新增独立测试文件
- 测试对象是否只是薄包装、纯转发、静态文案映射或无分支小函数；这类默认不测

## 优先补单测的场景

- 环境配置派生和默认值逻辑
- URL/path 拼接、子应用 entry 和 activeRule 派生逻辑
- 菜单树转换、路由匹配、选中态反推
- 前置流程队列排序、阻断结果处理、异常兜底和续跑位置
- 旧接口响应结构、用户信息规整、组织切换参数等历史兼容契约
- 修复已有 bug 时，能用纯逻辑复现的回归场景

## 不写或少写单测的场景

- 组件视觉细节
- CSS、布局间距、颜色、动画
- 真实接口联通性
- 简单展示组件、无分支包装组件
- 状态管理的普通 set/get
- 单纯把 service 结果转换的薄包装
- 纯静态文案映射，除非承载关键业务分流
- 只有一个布尔表达式的小工具函数，除非该表达式承载跨模块稳定契约

## 测试实现约束

- 优先测试纯函数，把复杂逻辑从组件中抽出来再测
- 不为了测试改动生产代码结构，除非能明显降低复杂度
- 不引入重型 mock 框架
- 不为了覆盖率写低价值测试
- 新增高风险逻辑时，同步补对应 Vitest 用例
- 优先把同一领域的用例合并到已有测试文件
- 新增测试文件时，文件名对应一个稳定领域契约，而不是对应一个很薄的实现文件
