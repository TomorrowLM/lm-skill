# Phase 1-2：调研与技术方案

用于把页面需求收敛为可确认的范围，并将已确认范围写成可执行的技术方案。Phase 1 只调研，Phase 2 只设计；两阶段都不得写业务代码。

## Phase 1：需求分析与技术调研

### 必须确认

- 页面目标、目标用户、核心流程、输入输出、边界状态和成功标准。
- 页面路由、文件位置、组件库选择和交互流程。
- 接口字段映射、状态枚举与展示映射。
- 可复用的现有组件、Hook、服务、执行流和样式体系。
- 现有页面、路由、组件、服务和样式的改造影响；只分析，不改动。

### 按条件加载

| 条件 | 动作 |
| --- | --- |
| 从零需求且无设计稿或接口文档 | 读取 `brainstorming`，先收敛需求。 |
| Figma、截图、UI 或 React 实现取舍 | 读取 `skill-routing`，仅路由当前需要的设计、视觉或 React 子技能。 |
| Swagger、OpenAPI 或 Figma 契约调研 | 读取 `mcp-exe` 的对应案例，获取范围确认所需信息。 |

### Phase 1 输出

展示需求共识、范围取舍、待决策点和调研摘要，等待用户确认后才进入 Phase 2。

## Phase 2：技术方案编写

### 方案必须明确

- 路由和文件位置。
- 组件拆分、Props、状态和职责边界。
- Hook、utils、store 的归属与边界。
- 类型、常量、枚举和状态展示映射。
- API 请求参数、响应字段、错误态和空态处理。

### 方案规则

- 用户已有技术方案时，审阅并补充缺失的实现细节。
- 用户未提供方案时，读取 `writing-doc` 并创建方案。
- 默认写入 `docs/design/YYYY-MM-DD-<topic>-design/index.md`。
- 方案涉及的每个页面必须注册到 `docs/pages/pages.yaml`；schema 和约束见 `pages-registry.md`。
- 提交用户审查前，清理占位符、内部矛盾、歧义和范围膨胀。

### Phase 2 输出

展示技术方案摘要和文档路径，等待用户确认后才进入 Phase 3。
