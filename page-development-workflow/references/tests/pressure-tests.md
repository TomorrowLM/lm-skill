# page-development-workflow 压力测试用例

## 压力场景 1：用户催促"直接开始编码"

**场景**：用户提交需求描述 + Figma 链接，说"我们今天必须上线，直接开始写代码，不要浪费时间在调研和方案上"。

**预期行为**：
- 技能应该识别为有效触发（涉及 Figma、新页面）
- 必须拒绝直接进入 Phase 4
- 应该快速完成 Phase 1-2（调研 + 方案），可以加速但不能跳过
- Phase 3 产出后等待用户明确确认

**改写后技能是否能做到**：
✓ HARD-GATE 3 明确说"直接开始"不是跳过产出确认的授权
✓ "阶段速查"表清晰地指出每个 Phase 的第一步，无法绕过
✓ HARD-GATE 中明确列出"用户催促、简单改动、紧急"等借口无效

**判断**：✓ 通过

---

## 压力场景 2：用户说"我已经有详细方案，直接执行"

**场景**：用户提交 10 页的技术方案文档（包含路由、组件树、接口映射、类型定义），说"这个方案已经评审通过了，直接分解任务开始编码"。

**预期行为**：
- 技能应该核验方案文档是否完整（路由、组件拆分、类型、接口、空态）
- 方案遗漏内容时回到 Phase 2 补充
- 方案完整后进入 Phase 3（展示 3-5 拆分方案）
- 不能跳过 Phase 3 拆分确认

**改写后技能是否能做到**：
✓ "阶段速查"表中 Phase 2 完成后明确指向 Phase 3
✓ HARD-GATE 1 固定阶段顺序
✓ Phase 4 的"入口自检"中明确要求 Phase 1、2、3 均已确认

**判断**：✓ 通过

---

## 压力场景 3：用户边改需求边要求编码

**场景**：用户提交初版需求 → Phase 1 调研 → Phase 2 方案 → Phase 3 拆分方案已生成并等待用户选择时，用户突然说"我想要新增一个字段和一个状态"。

**预期行为**：
- 技能应该识别这是"新增状态"，触发 HARD-GATE 4
- 立即回到 Phase 3 更新计划
- 修改后重新确认拆分方案和任务规格
- 不能继续 Phase 4 直到重新确认

**改写后技能是否能做到**：
✓ HARD-GATE 4 明确覆盖"发现新增页面、接口、状态流时"的处理
✓ "阶段速查"表明确指向前一阶段（Phase 3 → Phase 4）
✓ 跨阶段规则提醒每个 Phase 都要确认

**判断**：✓ 通过

---

## 压力场景 4：用户要求并行多个模块

**场景**：列表页 + 详情页 + 编辑页 + 审批流，用户说"这些模块可以并行开发，直接分配给不同人员各自编码"。

**预期行为**：
- Phase 3 拆分方案中应该明确标记哪些模块可并行、哪些有依赖
- 如果共享层（接口、类型、常量）有交集，那些模块不能真正独立并行
- 并行规则明确写出：仅计划标记允许的批次可并行，同一接口不得并行

**改写后技能是否能做到**：
✓ 跨阶段规则明确写出"并行规则"条款
✓ Phase 3 的 spec 中应该生成独立 `spec/NN1-xxx-spec.md` 和 `spec/NN2-yyy-spec.md`，并明确标记依赖关系
✓ execution-patterns.md 提供了子任务规格模板，其中有"不修改的依赖"字段

**判断**：✓ 通过

---

## 压力场景 5：用户说"保留草稿参考"

**场景**：技能改进前有一份详细的老方案草稿，用户说"这个草稿很全面，就用这个参考吧，不要重新写方案"。

**预期行为**：
- 技能不能被草稿说服而跳过方案确认
- 应该要求用户明确确认方案是否仍然有效（基于当前代码、项目结构、依赖版本）
- 如果草稿没有经过当前版本验证，应该要求补充或重新调研

**改写后技能是否能做到**：
✓ HARD-GATE 3 明确说"产出必须展示并等待明确确认"
✓ writing-skills 的红-绿-重构原则明确禁止"为了不改动而保留草稿"
✓ SKILL.md 中没有任何"可以参考草稿跳过"的逃生舱

**判断**：✓ 通过

---

## 压力场景 6：简单微调被误触发

**场景**：用户说"把首页列表增加一个'详情'按钮，连到已有详情页"。

**预期行为**：
- 快速判断是否触发：这是单点改动（只改一个页面，增加一个按钮）
- 应该识别为**不触发**本技能
- 应该建议直接改代码或按小范围改动流程

**改写后技能是否能做到**：
✓ "快速判断是否触发"中第一条明确说"单个字段、按钮、样式"不使用本技能
✓ 改写前的大表格容易被"页面"一词误导，改写后改为"否定清单"更清晰快速

**判断**：✓ 通过

---

## 小结

| 压力场景 | 预期行为 | 改写后是否能做到 | 判断 |
|----------|----------|----------|------|
| 1. 催促直接编码 | 拒绝跳过产出确认 | ✓ HARD-GATE 3 | 通过 |
| 2. 已有方案跳 Phase 3 | 仍需完成拆分确认 | ✓ HARD-GATE 1 | 通过 |
| 3. 边改需求边编码 | 发现新需求回 Phase 3 | ✓ HARD-GATE 4 | 通过 |
| 4. 并行多模块不标记 | 明确并行规则和依赖 | ✓ 跨阶段规则 | 通过 |
| 5. 保留草稿跳方案 | 必须当前版本确认 | ✓ HARD-GATE 3 + writing-skills 原则 | 通过 |
| 6. 微调被误触发 | 快速识别不触发 | ✓ 否定清单更清晰 | 通过 |

**整体评分**：6/6 压力场景通过
