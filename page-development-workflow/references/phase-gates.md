# Phase 门控清单

用于进入或结束任一 Phase 前快速核对输入、产出和门控条件。

## 全局门控

- Phase 1、2、3、5 结束后必须等待用户明确确认。
- Phase 4 前禁止写业务代码。
- 轻量路径只允许合并 Phase 1-3 的展示与确认，不允许省略阶段产出。
- 如果用户要求直接改一个小范围问题，本技能不触发。

## Phase 1：需求分析与技术调研

| 项目 | 内容 |
|------|------|
| 输入 | 用户需求、PRD、Figma、原型、Swagger / OpenAPI |
| 产出 | 需求共识、范围取舍、待决策点、技术调研摘要 |
| 门控 | 展示 Phase 1 产出并等待用户确认 |

完成标志：

- [ ] 已明确页面目标、目标用户、核心流程、输入输出、边界状态、成功标准。
- [ ] 已确认页面路由、文件位置、组件库、交互流程。
- [ ] 已梳理接口字段映射和状态展示映射。
- [ ] 已补充 MCP / GitNexus / 现有代码调研摘要（如适用）。
- [ ] Phase 2 所需输入齐备。

## Phase 2：技术方案编写

| 项目 | 内容 |
|------|------|
| 输入 | Phase 1 确认后的需求共识和调研摘要 |
| 产出 | 技术方案文档或对用户技术方案的审阅补充 |
| 门控 | 展示方案摘要和文档路径，等待用户确认 |

完成标志：

- [ ] 技术方案文档已创建或审阅补充完毕。
- [ ] 组件拆分、hooks / utils、类型常量、接口字段均已明确。
- [ ] 文档已自检：无占位符、无内部矛盾、无明显歧义。
- [ ] 文档已落盘到功能设计目录。

## Phase 3：制定实现计划

| 项目 | 内容 |
|------|------|
| 输入 | Phase 2 确认后的技术方案文档 |
| 产出 | 拆分方案、实现计划或子任务规格文件 |
| 门控 | 展示计划路径和执行编排，等待用户确认 |

完成标志：

- [ ] 已给出 3-5 种拆分方案，至少包含不拆分方案。
- [ ] 用户已选择拆分方案和执行方式。
- [ ] 已生成 `implementation-plan.md` 或多个 `<module>-spec.md`。
- [ ] 计划包含步骤顺序、串行阶段、可同步执行、不可同步执行、合流检查点。
- [ ] 如需修改现有模块，已完成影响面评估。

## Phase 4：编码实现

| 项目 | 内容 |
|------|------|
| 输入 | Phase 3 确认后的计划或子任务规格 |
| 产出 | 可运行代码和变更记录 |
| 门控 | **执行方式选择必须等待用户确认**（内联/子代理/MCP编排/多窗口），串行前置任务可立即内联执行 |

完成标志：

- [ ] 已向用户展示执行方式选项并获得确认。
- [ ] 只允许串行前置任务在确认前置执行；并行批次必须在用户选择方式后启动。

完成标志：

- [ ] 已按计划顺序执行。
- [ ] 只并行计划中明确允许的批次。
- [ ] TDD 任务已遵循红-绿-重构。
- [ ] 每个并行批次后已完成合流检查。
- [ ] 变更范围记录清楚。

## Phase 5：测试验收

| 项目 | 内容 |
|------|------|
| 输入 | Phase 4 代码变更和变更记录 |
| 产出 | 自动化验证证据、手动验收记录、代码审查结论 |
| 门控 | 展示证据和审查结论，等待用户确认 |

完成标志：

- [ ] 已读取 `package.json` 并选择项目实际验证命令。
- [ ] test / typecheck / lint / build 已按项目可用脚本执行。
- [ ] 已阅读命令输出并记录结果。
- [ ] 已给出手动验收入口和核心测试点。
- [ ] 验收通过后已完成代码审查。
- [ ] 证据已落盘到 `evidence/phase5-verification.md`。

## Phase 6：收尾交付

| 项目 | 内容 |
|------|------|
| 输入 | Phase 5 验证结果、审查结论、未提交变更 |
| 产出 | 交付摘要、验证证据、遗留风险、提交记录（如授权） |
| 门控 | push / PR / 合并 / 发布前必须再次确认 |

完成标志：

- [ ] 已汇总验证证据和代码审查结论。
- [ ] 已检查变更范围只包含本次需求。
- [ ] 已提交，或已说明未提交原因。
- [ ] 已输出交付摘要和遗留风险。
