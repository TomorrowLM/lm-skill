# Phase 3：拆分方案与实现计划

用于制定实现计划、设计任务拆分方案和执行编排。

## 计划落盘规则

- 不拆分：写入 `docs/design/YYYY-MM-DD-<topic>-design/spec/implementation-plan.md`。
- 拆分：写入多个 `docs/design/YYYY-MM-DD-<topic>-design/spec/<NNx>-<module>-spec.md`，其中 `NN` 为两位数字序号（01、02、03…），反映执行顺序；同一批次内可并行的子任务用字母后缀区分（如 `02a`、`02b`）。
- `spec/` 只存放可执行交付物，不存放整体技术方案。
- `implementation-plan.md` 与 `<module>-spec.md` 默认二选一；除非用户明确要求保留总计划。

## 默认任务顺序

1. 创建类型定义。
2. 创建常量配置。
3. 创建 API 服务层。
4. TDD 循环：创建数据管理模块。
5. TDD 循环：创建 UI 组件。
6. TDD 循环：实现页面主入口。
7. 验证路由配置。

## 拆分方案类型

每次至少给出 3 种，最多 5 种，并且必须包含“不拆分”。

| 方案类型 | 拆分维度 | 适用场景 |
|----------|----------|----------|
| 不拆分 | 单一实现计划，顺序执行 | 单页面、低复杂度、任务数 ≤ 7 |
| 按页面/路由拆分 | 每个页面或路由一个子任务 | 列表页 + 详情页 + 编辑页等多页面 |
| 按技术层拆分 | 类型/API → UI 组件 → 页面整合 | 接口稳定，UI 可并行 |
| 按功能模块拆分 | 筛选区、表格区、弹窗区等 | 单页复杂但区域相对独立 |
| 混合拆分 | 共享层先行，再按页面或模块并行 | 多页面 + 共享基础设施 |

## 每个方案必须包含

1. 方案名称。
2. 拆分方式。
3. 子任务列表：名称、范围、产出文件、预估 token。
4. 执行编排摘要：顺序、并行批次、前置依赖、禁止并行项。
5. 执行方式建议：内联执行 / 多窗口并行 / MCP 编排 / 子代理驱动。
6. 优点和风险。
7. 推荐排序：⭐⭐⭐ 首选 / ⭐⭐ 备选 / ⭐ 可用。

## 方案展示模板

```md
## 任务拆分方案（共 N 个）

### 方案 A：不拆分，顺序执行 ⭐⭐
- 拆分方式：不拆分
- 子任务列表：
  1. 类型、常量、API 服务
  2. 数据管理模块
  3. UI 组件
  4. 页面整合和路由验证
- 执行方式：内联执行
- 优点：上下文连续，集成成本低
- 风险：token 消耗较大，不利于多人或多窗口并行

### 方案 B：按页面/路由拆分 ⭐⭐⭐
- 拆分方式：共享层先行，每个页面独立子任务
- 子任务列表：
  1. 共享层：类型、常量、API 服务
  2. 列表页：搜索、分页、空态
  3. 详情页：信息展示、操作按钮
  4. 编辑页：表单、校验、提交
- 执行方式：MCP 编排 / 多窗口并行
- 优点：页面之间独立，可并行
- 风险：共享契约变更需要同步

---
请选择方案（A/B/C/...），或提出调整意见。
```

## 执行编排必填项

每份计划或子任务规格必须包含：

1. 步骤顺序。
2. 串行阶段。
3. 可同步执行批次。
4. 不可同步执行项及原因。
5. 合流检查点。

推荐格式：

```md
## 执行编排

### 步骤顺序
1. 任务 A：类型与接口契约（串行，前置任务）
2. 任务 B：列表 UI 组件（可与任务 C 同步）
3. 任务 C：筛选 UI 组件（可与任务 B 同步）
4. 任务 D：页面集成与路由配置（串行，依赖任务 B/C）
5. 任务 E：验证与修复（串行，最终合流）

### 可同步执行
- Batch 1：任务 B、任务 C；原因：写入不同组件目录，只依赖任务 A 的稳定契约。

### 不可同步执行
- 任务 A 与任务 B/C：任务 B/C 依赖任务 A 的类型和接口契约。
- 任务 D 与任务 B/C：任务 D 消费 B/C 的组件 props 和导出入口。

### 合流检查点
- Batch 1 完成后检查组件导出、props 类型、页面集成 import、样式作用域。
```

## 默认禁止并行

- 修改同一文件或同一目录入口文件。
- 修改同一函数、组件、Hook、store、service 方法或类型定义。
- 一个任务依赖另一个任务产出的类型、接口字段、常量、路由或组件 props。
- 同时改动同一 API 契约的请求参数、响应类型和调用方。
- 同时改动共享样式、全局状态、鉴权、PWA、SSE 或构建配置。

## 子任务规格要求

每个 `<module>-spec.md` 必须独立可执行，包含：

- 背景和目标。
- 输入文档路径。
- 需要读取的现有文件。
- 允许修改的文件范围。
- 禁止修改的文件范围。
- 实现步骤。
- TDD 要求。
- 验收标准。
- 完成后报告格式。
