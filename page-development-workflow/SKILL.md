# 页面开发工作流

通用的功能页面开发标准化流程，适用于任何前端技术栈和项目类型。

## 铁律（不可违反）

1. **禁止跳阶段** — 必须按 Phase 1 → 2 → 3 → 4 → 5 → 6 顺序执行，不得跳过任何阶段
2. **禁止直接写代码** — Phase 4 之前不得编写任何业务代码（类型定义、常量、组件、页面均算代码）
3. **每阶段必须等用户确认** — 每个 Phase 完成后，必须向用户展示该阶段产出并等待用户明确确认（如「继续」「可以」「下一步」）才能进入下一个 Phase
4. **无产出不停留** — 每个 Phase 必须产出该阶段规定的交付物，不能空过

> 如果用户说「帮我开发 XX 页面」「实现这个设计稿」「按这个需求写页面」等触发词，**从 Phase 1 开始**，不得直接写代码。

## 快速开始

```
Phase 1: 需求分析 → [用户确认] → Phase 2: 技术方案编写 → [用户确认] → Phase 3: 实现计划 → [用户确认] → Phase 4: 编码实现 → Phase 5: 测试验收 → [用户确认] → Phase 6: 收尾交付
```

每个 `[用户确认]` 是一个硬性门控：展示当前阶段产出 → 等待用户回复 → 才能进入下一阶段。

## 技能分发

### skill-routing 子技能路由

在本工作流中，仅 **UI/视觉/React 实现** 相关的技能选择委托 `skill-routing` 判断：当 Phase 涉及 Figma 设计稿落地、视觉方向取舍或 React/Next.js 性能实践时，读取 `lm-skill/skill-routing/SKILL.md`，按用户意图路由到其子技能（`skills/figma-implement-design`、`skills/frontend-design`、`skills/vercel-react-best-practices`）。

> `skill-routing` 只路由其 `skills/` 目录下的子技能。gitnexus、brainstorming、writing-doc、token-saving、TDD、代码审查等技能不通过 skill-routing 分发，直接在对应 Phase 中按条件加载。

### 其他技能

以下技能由工作流各 Phase 按条件直接加载，不经过 skill-routing：

| 技能 | 触发条件 | 使用阶段 |
|------|---------|---------|
| `brainstorming` | 从零开始的需求，无 Figma 无 Swagger | Phase 1 |
| `gitnexus-exploring` | 项目已有 GitNexus 索引，探索可复用代码 | Phase 1 |
| `writing-doc` | 用户未提供技术方案文档 | Phase 2 |
| `gitnexus-impact-analysis` | 项目已有 GitNexus 索引，评估影响面 | Phase 3 |
| `test-driven-development` | 编码阶段的 TDD 循环任务 | Phase 4 |
| `executing-plans` | 多窗口并行或内联执行 | Phase 4 |
| `subagent-driven-development` | 子代理驱动执行 | Phase 4 |
| `gitnexus-refactoring` | 修改现有模块且有 GitNexus 索引 | Phase 4 |
| `verification-before-completion` | 自动化验证门控 | Phase 5 |
| `requesting-code-review` | 验收通过后代码审查 | Phase 5 |
| `token-saving` | 任务可能消耗大量上下文（横切） | 任意阶段 |

## 标准工作流

### Phase 1: 需求分析与技术调研

> **前置逻辑** — 进入本阶段需确认：
>
> | 维度 | 内容 |
> |------|------|
> | **依赖 Skill** | 见「技能分发」段（UI/视觉类 → skill-routing；其他 → 直接按条件加载） |
> | **依赖 MCP** | 见「技能分发」段 |
> | **输入** | 用户需求描述（可能包含 PRD / 设计稿链接 / 接口文档链接 / 原型图） |
> | **产出** | brainstorming 设计共识 + 页面开发补充调研摘要；若涉及 Figma/Swagger 则附带 MCP 返回的数据摘要 |

**复用 brainstorming 产出：**

- 需求目标、目标用户、核心流程、输入输出、状态与边界、成功标准
- 已确认的方案约束、范围取舍和待技术方案细化的决策点

**页面开发专属确认：**

- 页面路由路径和文件位置
- UI 组件库选择，优先复用项目已有组件
- 交互逻辑和用户操作流程
- 数据结构与接口字段映射
- 状态枚举值与展示映射关系

**页面工作流补充调研：**

- 如有 Swagger/API 文档，补充 MCP 返回的数据摘要
- 如有 Figma 设计稿，补充 MCP 返回的 UI 数据摘要
- 如项目已有 GitNexus 索引，补充可复用组件、Hook、服务和现有执行流

**Phase 1 完成标志（必须全部产出）：**
- [ ] 已复用并展示 brainstorming 的设计共识、范围取舍和待细化决策点
- [ ] 已确认页面路由、组件库、交互流程、接口字段映射和状态展示映射
- [ ] 已补充页面开发所需的 MCP / GitNexus 调研摘要（如适用）
- [ ] 已确认 Phase 2 技术方案编写所需输入齐备

> **⛔ 门控：** 向用户展示以上产出，等待用户确认后才能进入 Phase 2。不得自行假设用户同意。

#### GitNexus 代码探索（已有索引的项目）

在需求分析阶段，用 GitNexus 快速了解现有代码结构，避免重复造轮子：

```
1. READ gitnexus://repo/{name}/context    → 检查索引是否最新
2. gitnexus_query({query: "<业务概念>"})  → 找到相关的现有模块和执行流
3. gitnexus_context({name: "<现有组件>"}) → 了解可复用的组件、Hook、服务
```

**用途：**
- 发现可复用的组件、Hook、工具函数
- 了解现有的状态管理模式和 API 服务组织方式
- 避免与现有模块产生命名冲突或职责重叠

**索引状态检查：**

| 情况 | 判断方式 | 处理 |
|------|---------|------|
| 索引不存在 | context 返回 "No index found" | 跑 `npx gitnexus analyze` 建立索引 |
| 索引过期 | context 返回 "Index is stale" | 跑 `npx gitnexus analyze` 重建索引 |
| 索引最新 | context 返回正常数据 | 直接使用 |

> 可用 `npx gitnexus status` 查看索引时间和符号数量，判断是否需要重建。
> 重建后重新 READ `gitnexus://repo/{name}/context` 验证索引已加载。

#### MCP 工具集成

在需求分析阶段，根据用户提供的资源类型，使用对应的 MCP 工具获取详细信息。

详细的工具参数和示例见 `references/mcp-integration.md`。

- **Swagger/API 接口文档** → 使用 `lm-mcp-server` 的 `get_swagger_mcp` 获取接口详情
- **Figma 设计稿** → 使用 `Framelink Figma MCP Server` 的 `get_figma_data` 获取 UI 数据

### Phase 2: 技术方案编写

> **前置逻辑** — 进入本阶段需确认：
>
> | 维度 | 内容 |
> |------|------|
> | **依赖 Skill** | 见「技能分发」段（UI/视觉类 → skill-routing；其他 → 直接按条件加载） |
> | **依赖 MCP** | 见「技能分发」段 |
> | **输入** | Phase 1 确认后的设计共识、页面专属确认和补充调研摘要 |
> | **产出** | 技术方案文档（组件拆分、hooks/utils、常量类型、接口字段均已明确）；或对用户提供的技术方案文档的审阅补充意见 |

**用户提供技术方案文档时：** 审阅并补充实现层面的细节，必要时整理为本次工作流的统一技术方案文档。

**用户未提供技术方案文档时：** 使用 `writing-doc` 技能按「前端功能技术方案文档模板」创建新文档。

**文档落盘与审查：**

- 将确认后的整体技术方案写入 `docs/design/YYYY-MM-DD-<topic>-design/index.md`
  - （用户对规格位置的偏好优先于此默认值）
- 如果可用，使用 elements-of-style:writing-clearly-and-concisely 技能
- 将技术方案文档 commit 到 git
- 提交用户审查前做技术方案自检：扫描占位符、内部矛盾、范围过大和可被多种方式理解的需求
- 技术方案自检发现问题时直接内联修复，再请用户审查技术方案文档

**审阅/补充要点：**

1. **确认路由和文件位置** — 根据项目目录规范确认页面文件路径
2. **细化组件拆分** — 基于页面架构图，明确每个组件的 props、状态和职责边界
3. **确认 hooks 和 utils** — 明确哪些逻辑封装为内部 hook、哪些提取为公共 hook/utils
4. **确认常量和类型** — 检查状态映射、枚举值、TypeScript 类型是否完整
5. **确认接口字段** — 核对 API 请求参数和响应字段的类型定义

**Phase 2 完成标志：**
- [ ] 技术方案文档已创建或已审阅补充完毕
- [ ] 组件拆分、hooks/utils、常量类型、接口字段均已明确
- [ ] 技术方案文档已自检、落盘并 commit
- [ ] 用户已审查技术方案文档

> **⛔ 门控：** 向用户展示技术方案文档（或补充内容）和文档路径，等待用户确认后才能进入 Phase 3。

### Phase 3: 制定实现计划

> **前置逻辑** — 进入本阶段需确认：
>
> | 维度 | 内容 |
> |------|------|
> | **依赖 Skill** | 见「技能分发」段（UI/视觉类 → skill-routing；其他 → 直接按条件加载） |
> | **依赖 MCP** | 见「技能分发」段 |
> | **输入** | Phase 2 确认后的技术方案文档 |
> | **产出** | 实现计划文件；如需拆分，则生成多个子任务规格文件；文件统一保存到 `docs/design/YYYY-MM-DD-<topic>-design/spec/`；执行方式已选定 |
> | **⚡ 决策点** | 规模判断（≥3 个独立模块 / token 不够 / 无共享依赖 → 触发拆分）；执行方式选择（多窗口并行 / 子代理驱动 / 内联执行 / 直接实现） |

将 Phase 2 的技术方案文档作为依据，在本工作流内创建详细的实现计划。Phase 3 的计划由本工作流生成；Phase 4 可使用 `executing-plans` 执行已确认的实现计划或子任务规格。

**计划落盘规则：**

- 不拆分时，将实现计划写入 `docs/design/YYYY-MM-DD-<topic>-design/spec/implementation-plan.md`
- 拆分时，为每个子需求生成独立子任务规格文件：`docs/design/YYYY-MM-DD-<topic>-design/spec/<module>-spec.md`
- `spec/` 目录只存放可执行交付物：实现计划或子任务规格，不存放整体技术方案
- `implementation-plan.md` 与 `<module>-spec.md` 默认二选一：不拆分只生成前者，拆分只生成后者；除非用户明确要求保留总计划

**页面开发的任务顺序：**

1. 创建类型定义（TypeScript 接口/类型）
2. 创建常量配置（状态映射、选项列表等）
3. 创建 API 服务层（接口请求封装）
4. **TDD 循环** → 创建数据管理模块（状态管理、业务逻辑）
5. **TDD 循环** → 创建 UI 组件（列表项、卡片等）
6. **TDD 循环** → 实现页面主入口（整合所有组件）
7. 路由配置验证

> **TDD 循环** = 执行此任务时必须使用 `superpowers:test-driven-development` 的红-绿-重构循环（写失败测试 → 最少代码通过 → 重构），无论哪种执行方式。

#### 任务规模判断与拆分

制定计划前，先判断当前需求是否过大，是否需要拆分为多窗口并行执行。

**判断标准（满足任意一条即触发拆分）：**

| 信号 | 说明 |
|------|------|
| 需求涉及 3 个以上独立页面/模块 | 如同时改动任务列表页、任务详情页、事件详情页 |
| 预估单窗口 token 不够 | 需求文档 + 设计稿 + 接口文档内容量很大 |
| 子模块之间无共享状态、无顺序依赖 | 改模块 A 不影响模块 B 的代码文件 |

**拆分流程：**

1. 将需求按模块边界拆成 2-3 个独立子需求
2. 为每个子需求生成独立子任务规格文件，保存为 `docs/design/YYYY-MM-DD-<topic>-design/spec/<module>-spec.md`
3. 向用户说明拆分方案，推荐哪个窗口先启动

**拆分原则：**
- `spec/` 表示可执行交付物目录，不存放整体技术方案
- 每个子任务规格文件是独立可执行的——包含该模块所需的全部上下文（文件路径、接口、类型、完成标准）
- 子任务规格之间通过共享的类型定义和 API 服务层协调（类型和 API 层必须先完成，或包含在第一个子任务规格中）
- 如果存在共享依赖（如公共类型、公共组件），将其作为第一个子任务规格优先执行

**不需要拆分的情况：**
- 单页面改动，任务数 ≤ 7
- 子任务之间有紧密的顺序依赖
- 预估一个窗口足够完成

> 拆分决策和执行方式选择一起向用户展示，等待确认后再生成实现计划。

#### GitNexus 影响面评估（已有索引的项目）

编码前评估新模块对现有代码的影响：

```
gitnexus_impact({target: "<要修改或依赖的现有符号>", direction: "upstream"})
→ d=1（直接破坏）：必须同步更新
→ d=2（可能影响）：需要测试
→ d=3（传递效应）：需要关注
```

**什么时候跑：** 新页面需要修改现有模块（共享组件、服务层、状态管理）时，先评估爆炸半径再动手。

**Phase 3 完成标志：**
- [ ] 实现计划已生成并保存到 `spec/implementation-plan.md`；如已拆分，每个子任务规格均包含对应步骤
- [ ] 已判断是否需要拆分，若需拆分则已生成独立子任务规格文件
- [ ] 执行方式已由用户选择（多窗口并行 / 子代理驱动 / 内联执行 / 直接实现）

> **⛔ 门控：** 向用户展示实现计划，等待用户确认后才能进入 Phase 4。

### Phase 4: 编码实现

> **前置逻辑** — 进入本阶段需确认：
>
> | 维度 | 内容 |
> |------|------|
> | **依赖 Skill** | 见「技能分发」段（UI/视觉类 → skill-routing；其他 → 直接按条件加载） |
> | **依赖 MCP** | 见「技能分发」段 |
> | **输入** | Phase 3 确认后的实现计划（单文件或多子任务规格文件） |
> | **产出** | 可工作的代码 + 逐任务 git commit 记录；多窗口并行时各窗口独立提交、主窗口汇总审查 |
> | **⚡ 决策点** | 拆分时第一个窗口先跑共享依赖（类型/API 层），其余窗口可并行启动 |

**前置条件检查（缺一不可）：**
- ✅ Phase 1 需求分析已完成且用户已确认
- ✅ Phase 2 技术方案文档已创建/审阅且用户已确认
- ✅ Phase 3 实现计划已生成且用户已确认

> 如果以上任一条件不满足，**禁止编写代码**，回到对应阶段补齐。

按 Phase 3 生成的实现计划逐步执行。执行方式在实现计划中明确：

- **多窗口并行**（大任务推荐）— 拆分为独立子任务规格文件，在多个聊天窗口中各自执行 `superpowers:executing-plans`，主窗口汇总
- **子代理驱动** — 委托 `superpowers:subagent-driven-development`
- **内联执行** — 委托 `superpowers:executing-plans`
- **简单场景** — 直接按计划步骤顺序实现

**编码纪律：**
- TDD 任务必须按红-绿-重构循环（委托 `superpowers:test-driven-development`）
- 类型定义、常量配置、API 声明等声明式代码按计划直接编写
- 代码示例见 `references/code-examples.md`

#### 多窗口并行执行

当 Phase 3 判定需要拆分时，将大需求拆成多个独立子任务规格文件，在多个聊天窗口中并行推进。

**为什么用多窗口并行：**
- 单窗口 token 有限，大任务放一个窗口里上下文不够
- 独立模块之间没有顺序依赖，天然可以并行
- 不需要子代理基础设施，即开即用

**前置条件（必须满足）：**
- 子任务规格文件已保存到 `docs/design/YYYY-MM-DD-<topic>-design/spec/` 目录
- 共享依赖（公共类型、API 服务层）已包含在第一个子任务规格中或已完成
- 每个子任务规格文件是独立可执行的——新窗口拿到就能开工

**执行流程：**

```
主窗口（当前）                         新窗口 A                  新窗口 B
─────────────                         ─────────                ─────────
拆任务规格 → 保存 .md 文件
  │
  ├─→ 手动开新窗口 ──────────────→  读取 module-a-spec.md
  │                                  executing-plans 执行
  │                                  逐任务提交
  │                                  完成后报告
  │
  └─→ 手动开新窗口 ──────────────→  读取 module-b-spec.md
                                     executing-plans 执行
                                     逐任务提交
                                     完成后报告
  │
汇总审查 ←──────────────────────────────────────────────────────────┘
```

**主窗口职责：**
1. 拆任务规格、保存子任务规格文件
2. 输出新窗口启动指令（给用户复制粘贴用）
3. 所有窗口完成后，审查提交记录、运行集成验证

**新窗口启动指令模板：**

```
请读取 docs/design/YYYY-MM-DD-xxx-design/spec/module-a-spec.md，用 superpowers:executing-plans 执行这个子任务规格。
项目根目录是 /Users/zm/work/yqa-g-h5-urban，严格按计划步骤逐任务执行，
每完成一个任务就提交一次，不要跨任务合并。所有任务完成后报告结果。
```

**新窗口纪律：**
- 不继承主窗口的任何对话上下文——只能靠子任务规格文件了解任务
- 严格按子任务规格文件逐任务执行，不自行扩展范围
- 每个任务独立提交，commit message 引用子任务规格文件名和任务编号
- 完成后在窗口内报告：哪些任务完成、哪些有问题、需要主窗口注意什么

**汇总审查：**
- 用 `git log --oneline` 检查所有窗口的提交是否完整
- 运行 `pnpm lint && pnpm build:test` 验证集成后无冲突
- 如有冲突（两个窗口改了同一文件），在主窗口手动解决

### Phase 5: 测试验收

> **前置逻辑** — 进入本阶段需确认：
>
> | 维度 | 内容 |
> |------|------|
> | **依赖 Skill** | 见「技能分发」段（UI/视觉类 → skill-routing；其他 → 直接按条件加载） |
> | **依赖 MCP** | 见「技能分发」段 |
> | **输入** | Phase 4 完成后的代码变更 + 提交记录 |
> | **产出** | 验证通过的代码（lint / typecheck / test / build 全绿）；UI 手动验收记录；代码审查结论 |
> | **⚡ 决策点** | 验收失败 → 回到 Phase 4 修复 → 重走 Phase 5；Critical/Important 审查问题 → 修复后重新验收 |

#### 自动化测试门控

使用 `superpowers:verification-before-completion` 的完整门控方法论（运行命令 → 阅读输出 → 带证据陈述结论）。

**页面验收命令选择：**

- 先读取项目 `package.json`，按项目实际包管理器和 scripts 选择命令
- pnpm 项目优先使用 `pnpm`，npm 项目使用 `npm`，不要混用包管理器
- 若项目已有固定脚本，优先运行对应脚本；若没有脚本，再使用框架通用命令
- 执行前必须向用户列出本次实际采用的验证命令和选择理由

**页面验收常见命令：**

```bash
<pm> test src/pages/page-name/ -- --coverage   # 单元测试，按项目脚本调整
<pm> typecheck 或 <pm> exec tsc --noEmit         # 类型检查，按项目脚本调整
<pm> lint                                       # 代码规范，按项目脚本调整
<pm> build                                      # 构建验证，按目标环境脚本调整
# 有 GitNexus 索引：gitnexus_detect_changes({scope: "staged"})
```

#### 验收清单

**自动化验证（必须有输出证据）：**
- [ ] 所有单元测试通过（0 failures）
- [ ] TDD 红-绿-重构循环已遵循（见 `superpowers:test-driven-development` 验证清单）
- [ ] 覆盖了边界情况（空数据、错误状态、加载状态）
- [ ] TypeScript 类型检查通过（0 errors）
- [ ] ESLint 检查通过（0 errors, 0 warnings）
- [ ] 构建通过（exit 0）

**UI 手动验证：**

#### 步骤 1：给出手动测试入口

说明：写清楚用户应该访问哪个页面、点击哪个入口、进入哪个模块；如果是新路由，提供完整路径和必要的前置登录/权限条件。

#### 步骤 2：列出核心测试点

说明：用户至少需要检查这些点：

- [ ] 页面或模块是否能正常打开
- [ ] 文案、标题、按钮、提示信息是否正确
- [ ] 关键交互是否正常，例如点击、切换、展开、关闭、提交
- [ ] 关键状态是否完整，例如默认态、禁用态、空态、错误态
- [ ] 是否存在明显视觉问题，例如错位、遮挡、溢出、闪动
- [ ] UI 还原度符合设计稿
- [ ] 搜索/筛选功能正常
- [ ] 分页/加载更多正常
- [ ] 响应式布局在不同屏幕尺寸下正常
- [ ] hover 状态交互正常
- [ ] loading 状态展示合理
- [ ] empty 空态处理完整
- [ ] error 错误态处理完整
- [ ] 键盘可达性和焦点顺序正确

#### 步骤 3：给出手动验收方式

说明：要求用户按「通过/不通过 + 问题截图 + 复现步骤」记录结果；如涉及移动端或设计稿还原，补充设备型号、浏览器和屏幕尺寸。

#### 步骤 4：更新验收结果记录

记录：汇总用户已确认的验收点、未通过项、遗留风险和后续调整项。

红线信号见 `superpowers:verification-before-completion` 和 `superpowers:test-driven-development` 技能。

> **验收失败时：** 回到 Phase 4 修复问题，重新走 Phase 4 → Phase 5 循环，直到所有验收项通过。

#### 代码审查（验收通过后）

验收通过后，使用 `superpowers:requesting-code-review` 派遣 code-reviewer 子代理对页面代码做质量审查。

- Critical/Important 问题修复后，重新走验收 → 审查循环
- Minor 问题记录到 `// TODO(review)` 注释，集中清理

> **⛔ 门控：** 向用户展示自动化验证证据、手动验收记录和代码审查结论，等待用户确认后才能进入 Phase 6。

### Phase 6: 收尾交付

> **前置逻辑** — 进入本阶段需确认：
>
> | 维度 | 内容 |
> |------|------|
> | **依赖 Skill** | 见「技能分发」段（UI/视觉类 → skill-routing；其他 → 直接按条件加载） |
> | **依赖 MCP** | 见「技能分发」段 |
> | **输入** | Phase 5 验证结果、代码审查结论、未提交变更 |
> | **产出** | 已提交的代码、交付摘要、验证证据、遗留风险说明 |
> | **⚡ 决策点** | 若需要 push、创建 MR/PR、合并或发布，必须先获得用户明确确认 |

**收尾动作：**

1. 汇总 Phase 5 的自动化验证结果、手动验收结果和代码审查结论
2. 检查未提交变更，确认只包含本次需求范围内的文件
3. 按项目提交规范生成 commit message，必要时拆分提交
4. 如用户明确要求，协助创建 MR/PR 或输出 MR/PR 描述草稿
5. 输出交付摘要：修改内容、验证证据、文档路径、遗留风险、建议下一步

**Phase 6 完成标志：**
- [ ] 已汇总验证证据和代码审查结论
- [ ] 已确认变更范围符合本次需求
- [ ] 已按提交规范完成提交，或已说明未提交原因
- [ ] 已输出交付摘要和遗留风险

> **⛔ 安全门控：** push、创建 MR/PR、合并、发布、删除分支等共享或难回滚操作，必须等待用户明确确认后才能执行。

## 通用规范要点

### 目录结构

```
src/
├── services/              # API 服务层（按业务模块组织）
│   └── module-name/
│       ├── index.ts       # 接口请求方法
│       └── types.ts       # 接口类型定义
└── pages/
    └── page-name/
        ├── index.tsx              # 页面入口
        ├── types.ts               # 页面类型定义
        ├── constants.ts           # 页面常量配置
        ├── hooks/                 # 页面私有逻辑
        │   └── useXxxData.ts
        └── components/            # 页面私有组件
            └── ItemCard/
                ├── index.tsx
                └── types.ts
```

### 设计原则

- **职责分离**：UI 组件、业务逻辑、API 服务分离
- **类型安全**：所有数据流转使用明确的类型定义
- **组件复用**：抽取通用组件，避免重复代码
- **统一规范**：遵循项目代码风格和命名约定
- **样式类名规范**：优先使用 Tailwind 内置类（如 `p-3`、`rounded-xl`、`text-sm`），避免任意值写法（如 `p-[12px]`）；仅当内置类无法精确表达时才使用任意值

### 代码组织

- API 服务统一管理，按业务模块分类
- 类型定义集中维护，避免散落
- 常量配置独立文件，方便维护
- 组件封装适度，避免过度设计

## 适用场景

- 从零开发任何类型的前端页面

- 按照团队规范创建功能模块
- 重构现有页面结构
