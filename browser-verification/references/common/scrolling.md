# 滚动与视口验证协议

本文件适用于所有浏览器验证模式，不只适用于页面结构采集。根 `SKILL.md` 的滚动硬门控优先；本文件补充页面、表格、列表和嵌套滚动容器的执行细节。

## 1. 触发范围

遇到以下任一情况，必须读取并执行本协议：

- 路由、菜单、Tab、子应用、Dialog/Drawer 或详情页切换。
- 页面内容超出窗口视口，或存在独立的 `overflow`/滚动容器。
- 表格、列表、虚拟列表、分页之外的无限滚动、懒加载或滚动加载。
- 需要通过截图、DOM、MCP 或视觉分析判断页面是否完整。

## 2. 切换后的视口复位

每次切换后，在分析截图、DOM 或业务内容前：

1. 识别窗口滚动容器和所有可滚动的内部容器，记录容器定位信息。
2. 检查 `scrollTop`、可视区域、内容高度和是否存在更多内容；无法确认位置时按未确认处理。
3. 位置不是顶部或无法确认时，先将对应容器滚动到顶部，等待异步渲染和布局稳定。
4. 重新截图、采集 DOM，并与 MCP 返回的激活态、主要内容和 URL 对账。
5. 复位失败或容器无法区分时，当前节点只能标记 `unverified`/`blocked`，不能沿用切换前的中部/底部视口。

## 3. 页面和内部容器覆盖

- 窗口及每个内部滚动容器至少检查顶部、中部和底部；不要用窗口滚动代替内部容器滚动。
- 同时存在嵌套容器时，一次只改变一个容器，记录父容器和子容器的滚动状态，避免把子容器内容误归属到页面。
- 固定表头、吸顶工具栏和固定底部操作栏不代表已经覆盖滚动内容；仍需检查其下方实际内容。
- 每个检查点都要重新执行截图、DOM/MCP 采集和候选台账对账。

### 3.1 重复展示的处理

- 先比较滚动前后的 `scrollTop`、可视区域、内容高度以及截图/DOM/候选指纹，不能只凭“看起来一样”判断重复。
- `scrollTop` 没有变化：说明滚动没有生效；应重新定位实际滚动容器并重试，仍失败则标记 `unverified`/`blocked`，不能跳过当前区域。
- `scrollTop` 已变化但截图、DOM 和候选指纹相同：记录 `duplicate-checkpoint`，不重复分析同一展示，继续下一个滚动检查点或下一个区域。
- 重复展示只能减少重复分析，不能直接清空待处理队列或把整个页面标记为 `verified`；仍需满足连续稳定检查点、无未知候选和其他双重证据门控。

## 4. 表格、列表和懒加载

- 表格至少检查表头/首屏、内容中段和末屏；逐步滚动时补采新出现的行、行操作、分页替代控件、空状态和错误状态。
- 虚拟列表或懒加载内容以“连续 2–3 次滚动后没有新业务结构”为停止条件；仍有未知候选、加载中或请求失败时不能标记 `verified`。
- 无限滚动接近底部时等待加载稳定，再复采 DOM、截图和候选；不得只保存最后一屏。
- 新出现的按钮、Tab、行操作、Dialog/Drawer 入口必须加入当前节点的待处理队列，并递归执行根技能的逐层验证和双重验证。
- 滚动到下一个区域后，若新出现的卡片、统计块、列表行或控件命中已确认模板，且没有标题、权限、状态、路由、Tooltip、Tab 或子控件差异，记录 `covered-by-template`、实例定位和覆盖范围，跳过重复模板递归，继续下一个区域。模板相同但数据或业务语义不同，仍需记录实例，不得把实例数据混为一个节点。

## 5. 滚动后的证据闭环

每次滚动至少记录：

```text
scrollContainer, initialPosition, checkpoint, resetPerformed,
newCandidates, stablePasses, screenshotEvidence, domEvidence,
mcpStateEvidence, status, reason
```

候选按稳定 `id`、DOM 路径、行定位、文本和 occurrence 去重。单次底部快照、单次 DOM 返回或工具报告“滚动成功”只能产生候选，不能证明滚动范围已验证完成。
