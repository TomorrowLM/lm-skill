# 调试与审查类场景 token 优化

## 构建或测试失败

**步骤：**

1. 只保留：失败命令、退出码、首个根因错误、相关堆栈（顶部 10-15 行）。
2. 不保留完整构建日志、所有 warning、所有 test case 输出。
3. 定位根因后，只读与该错误直接相关的源文件行段。

**常见陷阱：**

- 把完整终端输出（几千行）粘贴到对话中。
- 在定位根因前就读取所有可能相关的文件。

## 日志分析

**步骤：**

1. 先定位：错误关键词、时间点、堆栈顶部。
2. 再扩展上下文：错误前后各 10-20 行。
3. 不读取完整日志文件。

**常见陷阱：**

- 从日志第一行开始逐行分析。
- 多个错误时逐个分析而不是先归类。

## PR / Diff 审查

**步骤：**

1. 先按文件分组，标记每个文件的改动类型（新增/修改/删除）和风险等级。
2. 只展开高风险改动详读，低风险改动只列文件名和行数。
3. 审查结论只包含阻塞问题和关键建议。

**常见陷阱：**

- 逐文件、逐行写审查意见。
- 对格式化/import 排序等机械变更也写详细评论。
