# 产出类场景 token 优化

## 写技能

先确认目标、触发条件、不适用边界和测试方式。只读目标技能的 `description`、`SKILL.md` 和被点名的 reference；不预加载所有 reference，不全量扫描所有技能。

**红阶段（基线测试）：**

- 只保留：测试场景、AI 的实际输出、违规点、失败模式。
- 多个失败案例先归类，按模式总结，不逐条列举相似违规。
- 不跑超过 3 个压力场景；够触发规则即可。

**绿阶段（写最小规则）：**

- 只针对观察到的失败写规则，不预防假想问题。
- 每条规则写完后检查：删除它会不会让已观察到的失败重新出现？不会就是多余的。
- 规则用祈使句，一行说清行为边界；不写解释性 preamble。

**重构阶段（迭代堵漏）：**

- 每次迭代只改当前失败的规则，不趁机重写整个技能。
- 新增规则优先合并到已有章节，不新建独立段落。
- SKILL.md 超过 250 行时，把长示例、完整工作流、背景说明下沉到 `references/`。

**结构内建优化：**

`writing-skills` 的三级渐进式披露（`description` → `SKILL.md` body → `references/`）本身就是 token 控制：
- `description` 决定是否触发，必须精准，避免误触发加载整个技能体。
- `SKILL.md` body 只放控制逻辑、红线和引用条件。
- `references/` 按需读取，AI 只在执行到对应步骤时才加载。

**不做的：**

- 不创建 `README.md`、`CHANGELOG.md`、`QUICK_REFERENCE.md`。
- 不把 reference 内容复制到 `SKILL.md` body 中"方便阅读"。
- 不在 `SKILL.md` 中重复 `description` 已经说明的触发条件。
- 不保留草稿阶段的全部中间产出。

## 改技能

先定位要改的章节和触发边界；只读取相关段落和必要 reference。回复只给差异、依据和下一步，不粘贴整份新版内容，除非用户要求。

## 测试技能

只保留测试用例、期望行为、实际偏差、评分和结论。子代理只返回结论、证据、风险、建议，不返回完整测试过程。

## 写代码

**步骤：**

1. 先读项目规则（AGENTS.md）、入口文件和相关符号。
2. 用 `grep_search` 定位要修改的代码段，用 `read_file` 读相关行段。
3. 够用即停——不为了"全面理解"读完整个模块。
4. 修改后只保留关键路径、影响范围和验证结果。

**常见陷阱：**

- 先读完整个文件再开始改——先定位再精读。
- 修改一个函数前读完它的所有调用方——先改，用 `get_errors` 验证。
- 在多项目 workspace 中读取无关项目的代码。

## 思考方案

**步骤：**

1. 先压缩：目标一句话、约束三条、可选方案两个、风险一个。
2. 不要把背景资料全文带入上下文，只引用关键事实。
3. 输出优先是决策和取舍，不是完整分析过程。

**常见陷阱：**

- 把需求文档、接口文档、设计稿原文全部粘贴到上下文。
- 逐条分析所有方案的优缺点，而不是先给结论再解释。
