# Token Saving

## 核心目标

把上下文当作预算管理：先确定问题边界，再按证据逐层加载信息，只保留会影响下一步决策的内容。

## 先判定是否需要本技能

满足任一条件就使用：

- 需要阅读 3 个以上文件、网页、日志或接口文档。
- 工具输出可能超过 200 行。
- 任务跨越多个阶段、多个窗口或多个子代理。
- 用户要求总结、压缩、减少 token、节省上下文或避免污染会话。
- 当前对话已经很长，需要继续推进但保留关键事实。

不适用：单句问答、简单计算、单文件小修、用户明确要求完整逐字输出。

## 工作流

### 1. 先设 token 预算

开始前用一句话写清：

- 当前目标是什么。
- 必须保真的信息是什么。
- 可以压缩或丢弃的信息是什么。

如果目标不清，先问一个选择题，不要先读大量材料。

### 2. 分层获取上下文

按这个顺序拿信息，够用就停：

1. 文件名、目录结构、标题、目录、摘要。
2. 精确搜索命中的片段。
3. 相关文件的大段读取。
4. 只有在必要时读取完整文件或完整网页。

避免“先全量读再筛选”。每次读之前说明它要验证哪个假设。

### 3. 控制工具输出

- 搜索时优先用具体关键词、路径范围和结果上限。
- 读文件时按章节或相关行段读取，不连续小段不要反复读。
- 终端命令用项目脚本验证，不打印无关依赖树、完整构建日志或完整锁文件。
- 网页资料只摘取与当前决策有关的事实，保留来源链接。
- 日志分析先定位错误关键词、时间点和堆栈顶部，再扩展上下文。

### 4. 压缩并替换上下文

每完成一个阶段，立即把上下文压缩成 5 类事实：

| 类型 | 记录内容 |
|---|---|
| 目标 | 用户真正要达成什么 |
| 决策 | 已确认的方案、边界和取舍 |
| 证据 | 文件路径、命令结果、来源链接 |
| 风险 | 仍不确定或可能出错的点 |
| 下一步 | 只保留马上要做的 1-3 个动作 |

压缩后不要再重复粘贴原始材料，除非用户要求或需要引用精确文本。

### 5. 市面常见高消耗场景处理

| 场景 | 省 token 做法 |
|---|---|
| 大仓库代码探索 | 先目录和符号搜索，再读入口文件；必要时派只读子代理返回路径和结论 |
| 长 PR / diff 审查 | 先按文件分组和风险分层，只展开高风险改动 |
| 构建或测试失败 | 只保留失败命令、退出码、首个根因错误、相关堆栈 |
| Figma / UI 还原 | 先读取节点结构和截图摘要，再下载必要资产；不要描述每个无关图层 |
| Swagger / API 文档 | 只查目标 tag、operationId 或模型；不要加载整份接口文档 |
| 网页调研 | 先找权威来源和发布日期，再摘决策相关事实 |
| 多代理协作 | 给子代理明确输出格式：结论、证据、风险、建议；禁止返回完整过程 |
| 长对话续接 | 先写短状态摘要，再继续；不要重述所有历史 |

### 6. 回复要短，但不能少证据

默认输出结构：

1. 结论或当前决策。
2. 关键证据，最多 3 条。
3. 下一步。

不要输出完整思考过程、完整工具日志、无关背景、重复的文件内容。

## 红线

- 不要为了省 token 跳过必要验证。
- 不要压缩掉用户明确要求保留的细节。
- 不要把不确定事实写成确定结论。
- 不要用“节省 token”为理由省略安全、测试、影响面或来源证据。
- 不要在一个回复里同时解决多个未确认的大范围问题；先收敛范围。

## 与其他技能集成

- `brainstorming`：只保留设计共识，不生成长规格。
- `gitnexus-exploring`：用知识图谱替代全仓库盲读。
- `systematic-debugging`：先定位根因，再读取相关上下文。
- `requesting-code-review`：子代理只返回阻塞问题和证据。
- `verification-before-completion`：验证输出只摘命令、退出码和关键结果。

## 完成检查

结束前确认：

- [ ] 当前回答只包含推进任务所需信息。
- [ ] 证据足够支撑结论。
- [ ] 未读取或粘贴无关大段内容。
- [ ] 下一步明确且数量不超过 3 个。
