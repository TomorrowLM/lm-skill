# Token Saving

## 核心目标

把上下文当作预算管理：先确定问题边界，再按证据逐层加载信息，只保留会影响下一步决策的内容。

## 先判定是否需要本技能

满足任一条件就使用：

- 需要阅读 3 个以上文件、网页、日志或接口文档。
- 工具输出可能超过 200 行。
- 任务跨越多个阶段、多个窗口或多个子代理。
- 用户要求总结、压缩、减少 token、节省上下文或避免污染会话。
- 任务需要写技能、改技能、测试技能、写代码、思考方案或访问多份文件。
- 任务涉及多项目 workspace、规范模板拼装、AGENTS/CLAUDE 文档同步或公共资源复用判断。
- 当前对话已经很长，需要继续推进但保留关键事实。

不适用：单句问答、简单计算、单文件小修、用户明确要求完整逐字输出。

## 工作流

### 1. 先设 token 预算

开始前用一句话写清：

- 当前目标是什么。
- 必须保真的信息是什么。
- 可以压缩或丢弃的信息是什么。

如果目标不清，先问一个选择题，不要先读大量材料。

### 2. 分层获取上下文

按这个顺序拿信息，够用就停：

1. 文件名、目录结构、标题、目录、摘要。
2. 当前项目已有清单、索引、AGENTS/README 中的约束摘要。
3. 精确搜索命中的片段。
4. 相关文件的大段读取。
5. 只有在必要时读取完整文件或完整网页。

避免“先全量读再筛选”。每次读之前说明它要验证哪个假设。

### 3. 控制工具输出

- 搜索时优先用具体关键词、路径范围和结果上限。
- 读文件时按章节或相关行段读取，不连续小段不要反复读。
- 多项目 workspace 中只读取当前上下文明确涉及的项目；不要为了“保险”扫描全部项目。
- 终端命令用项目脚本验证，不打印无关依赖树、完整构建日志或完整锁文件。
- 网页资料只摘取与当前决策有关的事实，保留来源链接。
- 日志分析先定位错误关键词、时间点和堆栈顶部，再扩展上下文。

### 4. 压缩并替换上下文

每完成一个阶段，立即把上下文压缩成 5 类事实：

| 类型 | 记录内容 |
|---|---|
| 目标 | 用户真正要达成什么 |
| 决策 | 已确认的方案、边界和取舍 |
| 证据 | 文件路径、命令结果、来源链接 |
| 风险 | 仍不确定或可能出错的点 |
| 下一步 | 只保留马上要做的 1-3 个动作 |

压缩后不要再重复粘贴原始材料，除非用户要求或需要引用精确文本。

### 5. 按任务类型分流

先判断当前任务属于哪一类，再套用对应省 token 路径。

| 场景 | 省 token 做法 |
|---|---|
| 写技能 | 先确认目标、触发条件、不适用边界和测试方式；只读目标技能的 `description`、`SKILL.md` 和被点名的 reference；不要全量扫描所有技能或复制完整参考资料。 |
| 改技能 | 先定位要改的章节和触发边界；只读取相关段落和必要 reference；回复只给差异、依据和下一步，不粘贴整份新版内容，除非用户要求。 |
| 测试技能 | 只保留测试用例、期望行为、实际偏差、评分和结论；子代理只返回结论、证据、风险、建议，不返回完整过程。 |
| 写代码 | 先读项目规则、入口文件和相关符号；够用即停；修改前后只保留关键路径、影响范围和验证结果。 |
| 思考方案 | 先压缩目标、约束、可选方案、风险；不要把背景资料全文带入上下文；输出优先是决策和取舍。 |
| 访问文件 | 先看目录、标题、摘要或搜索命中片段；必要时再读大段；避免无目标地读取完整文件。 |
| 访问网页 / 接口文档 | 先确认权威来源、目标 tag、operationId、模型或发布日期；只摘录影响决策的事实。 |
| 多代理协作 | 给子代理固定输出格式：结论、证据、风险、建议；禁止返回完整过程或大段原文。 |
| 长对话续接 | 先写 5 类事实摘要：目标、决策、证据、风险、下一步；之后只基于摘要推进。 |

### 6. 市面常见高消耗场景处理

| 场景 | 省 token 做法 |
|---|---|
| 大仓库代码探索 | 先目录和符号搜索，再读入口文件；必要时派只读子代理返回路径和结论 |
| 长 PR / diff 审查 | 先按文件分组和风险分层，只展开高风险改动 |
| 构建或测试失败 | 只保留失败命令、退出码、首个根因错误、相关堆栈 |
| Figma / UI 还原 | 先读取节点结构和截图摘要，再下载必要资产；不要描述每个无关图层 |
| Swagger / API 文档 | 只查目标 tag、operationId 或模型；不要加载整份接口文档 |
| AGENTS / 规范模板生成 | 只读取命中的技术栈模块；默认保留规则，示例代码、完整目录树和清单明细按需展开 |
| 公共组件 / 公共资源复用 | 先读当前 AGENTS 清单判断；清单缺失、疑似过期或需要新增调整时，才最小范围扫描目录 |
| 网页调研 | 先找权威来源和发布日期，再摘决策相关事实 |

### 7. 回复要短，但不能少证据

默认输出结构：

1. 结论或当前决策。
2. 关键证据，最多 3 条。
3. 下一步。

不要输出完整思考过程、完整工具日志、无关背景、重复的文件内容。

## 红线

- 不要为了省 token 跳过必要验证。
- 不要压缩掉用户明确要求保留的细节。
- 不要把不确定事实写成确定结论。
- 不要用“节省 token”为理由省略安全、测试、影响面或来源证据。
- 不要在一个回复里同时解决多个未确认的大范围问题；先收敛范围。
- 不要读取未命中的技术栈模块、无关 workspace 项目或完整模板，只因为它们“可能有用”。

## 与其他技能集成

- `brainstorming`：只保留设计共识，不生成长规格。
- `gitnexus-exploring`：用知识图谱替代全仓库盲读。
- `systematic-debugging`：先定位根因，再读取相关上下文。
- `requesting-code-review`：子代理只返回阻塞问题和证据。
- `verification-before-completion`：验证输出只摘命令、退出码和关键结果。

## 完成检查

结束前确认：

- [ ] 当前回答只包含推进任务所需信息。
- [ ] 证据足够支撑结论。
- [ ] 未读取或粘贴无关大段内容。
- [ ] 下一步明确且数量不超过 3 个。
